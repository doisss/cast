## 1. Назначение

SARBAR — оркестратор безопасности контейнеров и образов. Он **не является**
сканером уязвимостей: у него нет своей CVE-базы и нет парсеров экосистем.
Вместо этого он решает задачу, которую не решает ни один отдельный инструмент:

1. определить тип цели по тому, что ввёл пользователь;
2. объяснимо выбрать движки под профиль риска;
3. нормализовать вывод разных сканеров в одну модель находки;
4. дедуплицировать и скоррелировать результаты;
5. выполнить собственный набор проверок (`sarbar-checks`), которые закрывают то,
     что универсальные сканеры проверяют хуже всего;
6. свести всё к композитному risk score;
7. применить политику fail/pass;
8. выдать единый отчёт в четырёх форматах;
9. сохранить прогон в локальную историю.

### Что здесь НЕ наше (граница, которую важно защищать на защите)

| Не наше | Почему |
|---|---|
| CVE-база | Trivy/Grype привозят свои базы |
| Парсеры экосистем | lockfile/package manager — задача специализированных инструментов |
| Свой kernel-модуль / агент | Runtime = `docker inspect` + эвристики, без eBPF |

## 3. Инварианты

Это список того, что не должно происходить никогда. Нарушение любого пункта —
баг высшего приоритета, независимо от того, проходит ли он тесты.

| # | Инвариант | Почему важен |
|---|---|---|
| I-1 | **Упавший или отсутствующий сканер не может давать PASS.** Если ни один сканер не отработал успешно, вердикт не может быть `pass`, а в отчёте обязан быть флаг деградации. | Сканер безопасности, который зелёный на упавшем движке, опаснее отсутствия сканера |
| I-2 | ~~Включённые собственные проверки не отключаются ничем.~~ **Снят в 0.4.0:** собственных проверок в проекте больше нет, I-3 тоже снят | — |
| I-3 | **`--offline` не отключает сканеры.** Офлайн означает «использовать локально сохранённую базу уязвимостей», а не «ничего не проверять». | Раньше офлайн обнулял список сканеров и давал пустой PASS — ровно то, чего офлайн делать не должен |
| I-4 | **Бинарь сканера исполняется по абсолютному пути** и публикуется в PATH-каталог, чтобы работать и как отдельная команда. | `~/.sarbar/bin` не в PATH — источник тихих отказов |
| I-5 | **Невозможность разрешить цель — это ошибка с кодом возврата 2,** а не пустой отчёт с PASS. | Опечатка в пути не должна давать зелёный CI |
| I-6 | ~~Покрытие поиска не может быть усечено молча.~~ **Снят в 0.4.0** вместе с собственными проверками; правило осталось бытуальным для отчётов сканеров | — |
| I-7 | **Ни одно поле вывода не попадает в HTML без экранирования.** | Отчёт открывают в браузере; имя пакета приходит из внешнего источника |
| I-8 | **SARIF-вывод валиден по схеме `sarif-2.1.0`.** В частности, `rules[]` не содержит дубликатов. | Формат заявлен как пригодный для GitHub Code Scanning |
| I-9 | **Severity нормализуется из любого диалекта сканера,** включая приоритеты Falco. | `UNKNOWN` имеет вес 0 и не влияет на риск |
| I-10 | **Сборка пакета не ходит в сеть.** Установка сканеров — только явная команда `sarbar setup`. | Сборка должна быть герметичной и воспроизводимой |
| I-11 | **Файлы профилей из `sarbar/policies/` доходят до установленного пакета.** | Иначе слой политик мёртв у реального пользователя |
| I-12 | **Каждая строка в выводе объяснима.** Молчаливый пропуск, битый предикат, недоступный сканер — всё попадает в `diagnostics`. | Молчание в security-инструменте читается как «всё чисто» |
| I-13 | **В отчёте нет вымышленных данных.** Движок mock удалён; ни при каких условиях отчёт не содержит несуществующих CVE. | Выдуманная CVE неотличима от настоящей, попав в отчёт |
| I-14 | **Установленный сканер либо работает, либо помечен как сломанный.** Проверка `--version` обязательна; неисполняемый файл удаляется и не рапортуется как установленный. | Именно так в систему попал `.debug`-файл вместо бинаря |
| I-15 | **Сканер не запускается на цель, которой нет.** | Бессмысленный вызов и риск зависнуть на несуществующем пути |
| I-16 | **Ни одна находка в отчёте не придумана sarbar.** В проекте нет ни одного модуля с собственными проверками; каждый ID в отчёте принадлежит сканеру. | Расширение I-13: запрет не только на mock, но и на любые собственные правила |
| I-17 | **Установленный сканер запускается как команда без дополнительных аргументов.** `falco` без `-c` обязан работать. | Falco требует `/etc/falco/falco.yaml`. Обёртка-визитка решала это подменой пути, но подменять путь — обман; правильно положить конфигурацию в `/etc/falco` (сессия F) |
| I-18 | **`install.sh` доводит дело до конца.** Скрипт обязан работать на PEP 668-системах (Debian, Kali) и сам выбирать допустимый способ установки. | На машине пользователя `pip install` отказывался, скрипт падал |

### Сессия A — `ses_f1d38c582ffe8urYlJqbz11bMI` («Random input»)

#### A.1 Исходная постановка (3 проблемы от пользователя)

Пользователь сообщил:

1. `sarbar engines` показывает `cast-checks`, и в выводе скана движок выводится
   как `trivy, falco, cast-checks` — лишний шум.
2. `trivy` скачивает CVE-базу при прямом вызове, но не скачивает при вызове из
   sarbar; результаты отличаются. `trivy` не работает в shell вообще.
3. `falco` не запускается: `zsh: exec format error: falco`.

#### A.2 Решения пользователя (эти решения — источник регрессий A.7 и A.8)

#### A.4 Исследование Falco (почему он не работает)

Ассистент установил фактическую причину через GitHub API: **начиная с версии
0.40.0 в релизах Falco публикуются только `.debug`-артефакты
(`falco-x86_64.debug`), а не исполняемые `.tar.gz`/`.deb`.** Проверены 0.45.0,
0.44.0 — только debug. Установка официальным скриптом требует root.

Вывод сессии: положить в `~/.sarbar/bin` можно только через официальный скрипт
(с root) либо через debug-файл (нерабочий).

#### A.5 Проблема с debug-файлом (подтверждена в сессии B)

Ассистент вручную скачал `falco-x86_64.debug` в `~/.sarbar/bin/falco`.
Результат (подтверждено независимо в сессии B):

```
$ file ~/.sarbar/bin/falco
ELF 64-bit LSB executable, x86-64, dynamically linked, interpreter *empty*, ...
$ ~/.sarbar/bin/falco --version
zsh: exec format error: /home/d/.sarbar/bin/falco
```

Файл не исполняется: у него отсутствует интерпретатор, указанный в
ELF-заголовке. `sarbar engines` при этом показывает `falco available=yes`.

#### A.7 Регрессия, оставшаяся от сессии A

Условие `not engines_used` в `orchestrator.py` перепутало две разные вещи:
«сканер установлен» и «сканер отработал». Установленный, но не запустившийся
trivy считался «использованным», из-за чего собственные проверки отключались.
Реализация к тому же распространила подавление на `--offline` — чего никто не
просил. Это инварианты **I-1, I-2, I-3**, нарушенные в сессии A и исправленные
в сессии B.

#### A.8 Регрессия, внесённая последним действием сессии A

Финальная правка `sarbar/setup.py` в сессии A **заменила** рабочую
`install_falco` (официальный скрипт, вариант A-2.4) на новую функцию
`find_binary_asset_url()` + `download_and_install_binary()`. Сессия оборвалась
на этом шаге, не проверив результат. Итог:

- скачивается debug-файл вместо бинаря;
- `download_and_install_binary()` сохраняет архив как исполняемый файл и
  **всегда** печатает `falco installed`, независимо от результата;
- на диске остался нерабочий `~/.sarbar/bin/falco`.

Сессия завершилась в регрессированном состоянии — это и есть корень A.5.

#### C.3 Установка без root

| Шаг | Как |
|---|---|
| Найти пакет | Чтение индекса `download.falco.org/packages/deb/dists/stable/main/binary-amd64/Packages.gz`, выбор самой свежей версии **без** `Depends: dkms` |
| Извлечь | `dpkg-deb -x` (запасной путь: `ar` + `tar`) — файлы `usr/bin/falco` и `etc/falco/*` |
| Куда | система: `/usr/bin/falco` и `/etc/falco/`; запасной режим: `~/.sarbar/bin/falco` и `~/.sarbar/etc/falco/` |
| Опубликовать | система: ничего, бинарь уже в `/usr/bin`; запасной режим: симлинк в `~/.local/bin/falco` |
| Проверить | `--version`; неисполняемый файл **удаляется** (инвариант I-14) |

**Почему нужен `etc/falco`:** бинарь без конфигурации не стартует —
`Error: You must create a config file`. Без правил: `Error: You must specify at
least one rules file`. Обе ошибки проверены на живом бинаре.

Ключевая находка: в 0.3.0 **исправлено моё собственное подозрение** из сессии B.
Я записал, что флаг `-M 10` «подозрителен». По `falco --help` для 0.45.0:
`-M <num_seconds>` — это **секунды**, не число событий. Флаг корректен.
А вот `-A` действительно удалён в 0.42: `Error: Option 'A' does not exist` —
это был настоящий баг, из-за которого falco падал сразу и при этом
засчитывался как отработавший.

#### D.3 Что такое адаптер и что в нём менялось

**Адаптер** — это переводчик между sarbar и внешней программой. Trivy, Grype,
Dockle и Falco — четыре независимые программы, написанные разными людьми. У
каждой свой формат вывода, свои названия severity, свои коды возврата. Адаптер
(`sarbar/engines/__init__.py`) — это класс, который запускает программу и
превращает её вывод в единый `Finding`.

Схема:

```
  sarbar scan alpine:3.19
        │
        ├── TrivyEngine.run("alpine:3.19", "image")
        │      subprocess: trivy image --quiet --format json ...
        │      json.loads(...)             ← разбор чужого JSON
        │      → [Finding, Finding, ...]    ← единый формат
        │
        ├── GrypeEngine.run(...)   → то же самое
        │
        └── FalcoEngine.run(...)   → то же самое
                    │
             результат сравнивается и дедуплицируется
```

Правки в адаптере Falco за сессии C и D:

| Что | Зачем |
|---|---|
| Убран флаг `-A` | Удалён в Falco 0.42: `Error: Option 'A' does not exist`. Falco падал сразу, а sarbar при этом засчитывал его как отработавший |
| Добавлены `-c <config>` и `-r <rules>` | Без них Falco не стартует: `Error: You must create a config file` |
| Добавлен `-U` | Без буферизации события не успевают прочитаться за короткое окно |
| `-M` = длительность окна в секундах | Моё подозрение из отчёта №1 оказалось неверным; значение стало настраиваемым, по умолчанию 20 с |
| Поиск `falco.yaml` и `falco_rules.yaml` | Пути к конфигурации проверяются заранее; отсутствие даёт понятное сообщение вместо падения |
| Распознавание отсутствия драйвера | `Plugin requirement not satisfied` больше не превращается в «0 событий», а сообщает, что нужен `sudo falcoctl container install` |
| Таймаут переформулирован | «В окне N с событий не было» вместо «нужен root». Это разные утверждения: первое — факт, второе было предположением |

Правки в адаптере Trivy:

| Что | Зачем |
|---|---|
| Параметр `offline` и флаги `--skip-db-update --offline-scan` | Офлайн должен использовать локальную базу, а не выключать сканер |
| `download_db()` и `db_present()` | Предполёт: скачать базу один раз, если её нет |
| Проверка маркера `SchemaVersion` в выводе | Trivy завершается с ненулевым кодом и при найденных уязвимостях, и при ошибке. Наличие JSON-документа — надёжный признак успеха |
| Подсказка про `sarbar offline` в диагностике | Раньше ошибка БД выглядела как пустой результат |

#### D.4 Ответ на вопрос «зачем тогда установка от root, если можно без root»

Бинарь — можно, и он ставится без root. Но **команда `falco` без аргументов**
требует `/etc/falco/falco.yaml`, а этот путь может создать только root:

```
$ falco
Error: You must create a config file at /etc/falco/falco.yaml or by passing -c
```

Варианты были три:

| Вариант | Результат |
|---|---|
| Требовать root | Работает, но отказывает пользователям без sudo |
| Копировать `/etc/falco` при установке от root | То же самое, только опционально |
| ~~Опубликовать обёртку~~ | ~~`falco` работает без root~~ |

> **Устарело в сессии F.** Третий вариант отменён решением владельца. Обёртка
> была не решением задачи, а сокрытием её: она подсовывала falco путь, чтобы тот
> не заметил, что конфигурации на месте нет. Правильно — положить конфигурацию в
> `/etc/falco`, а если нет root, признать это честно и попросить пароль в момент
> сканирования. В `~/.local/bin/falco` кладётся не симлинк, а маленький
shell-скрипт, который подставляет нашу конфигурацию:

```sh
REAL="/home/d/.sarbar/bin/falco"
CONF="/home/d/.sarbar/etc/falco/falco.yaml"
RULES="/home/d/.sarbar/etc/falco/falco_rules.yaml"

case " $* " in
  *" -c "*|*" --config "*) exec "$REAL" "$@" ;;
esac
[ -f "$CONF" ] || exec "$REAL" "$@"
[ -f "$RULES" ] && set -- "$@" -r "$RULES"
exec "$REAL" -c "$CONF" "$@"
```

Если пользователь передаёт свой `-c`, он побеждает — скрипт не мешает.
Проверено: `falco --version`, `falco -h`, `falco -L` и bare `falco` работают.

Этот абзац описывает состояние на конец сессии D и сохранён как история
ошибочного решения, а не как руководство. Действующая схема — в сессии F.

#### D.6 Где скачиваются базы уязвимостей

Это делает **trivy сам**, в своём собственном кэше. sarbar на путь не влияет и
ничего не дублирует.

| Путь | Что | Размер |
|---|---|---|
| `~/.cache/trivy/db/trivy.db` | база уязвимостей (SQLite) | **1.4 ГБ** |
| `~/.cache/trivy/db/metadata.json` | версия и время следующего обновления | 153 байта |
| `~/.cache/trivy/fanal/` | кэш слоёв образов — распакованные слои, чтобы не скачивать их повторно | — |
| `~/.cache/trivy/policy/` | политики проверок | — |

Содержимое `metadata.json` на момент проверки:

```json
{
    "Version": 2,
    "NextUpdate": "2026-10-06T13:07:51Z",
    "UpdatedAt":  "2026-10-05T13:07:51Z",
    "DownloadedAt": "2026-10-05T16:52:11Z"
}
```

Механика: при обычном `sarbar scan` trivy сам проверяет `NextUpdate` и, если срок
прошёл, молча обновляет базу. Поэтому «онлайновый» скан может внезапно
затормозить на минуту — так и было в сессии B. Чтобы этого не было, есть
`sarbar offline`: он скачивает базу один раз, а дальше работает с
`--skip-db-update`, и сеть не нужна совсем.

Переопределить путь можно штатным флагом trivy `--cache-dir`, но sarbar его не
переопределяет — используется стандартный кэш, чтобы `trivy` из shell и
`sarbar` работали с одной и той же базой.

#### D.7 О каком драйвере речь

Falco не читает файлы и не опрашивает образы. Он подписывается на **события
ядра** — системные вызовы процессов, сетевые соединения, операции с файлами —
и применяет к ним правила.

Чтобы получать эти события, ядро должно отдавать их инструменту. Есть два
способа:

| Способ | Что это | Требует |
|---|---|---|
| **eBPF** | Современный механизм: маленькие программы, встроенные в ядро, которые ядро выполняет при каждом системном вызове | Права root для загрузки программы |
| **kmod** | Модуль ядра, подгружаемый через `modprobe` | DKMS, компилятор, пересборка при обновлении ядра |

Без одного из них ядро просто не отдаёт события, и Falco не с чем работать. Отсюда
ошибка, которую видно на этой машине:

```
Error: Plugin requirement not satisfied, must load one of: container (>= 0.4.0)
```

Раньше sarbar в такой ситуации писал «0 событий» — то есть утверждал, что

### Сессия F — «как положено в линукс»: /usr/bin, /etc/falco, sudo по требованию

Дата: 5 октября 2026. Версия 0.4.1.

Три вопроса владельца и что с ними сделано.

#### F.1 «Почему они в локал? Ты же хотел в /usr/bin»

Причина была одна: у меня не было root, а `/usr` и `/etc` без него не
записываются. Вместо отказа владелец получил костыль, а костыль исказил
картину. Владелец прав: если уж ставить системно — ставить по правилам.

Убрано. `install.sh` в режиме root кладёт:

| Что | Куда |
|---|---|
| `sarbar`, `cast` | `/usr/bin/` |
| `trivy`, `falco` | `/usr/bin/` — обычные бинарники, не симлинки, не скрипты |
| настройки falco | `/etc/falco/` |
| история прогонов | `/var/lib/sarbar/` |

Ровно как у дистрибутива. Режим без root сохранён, но переименован в
запасной и честно назван: `~/.sarbar/bin/` + симлинк в `~/.local/bin/`.

#### F.2 «Убери обход визитки. Если falco нужен root — пусть sarbar спросит пароль»

Скрипт-визитка `~/.local/bin/falco` **удалён полностью**. Причина его
существования была в том, что `/etc/falco/` закрыт для обычного пользователя,
а голый `falco` без конфигурации не стартует. Правильное решение — не подсовывать
путь, а положить конфигурацию туда, где она и должна лежать.

Схема запроса пароля (решение владельца): **в момент сканирования**.

```
sarbar scan abc123        # falco нужен
  -> sudo -v               # пароль спрашивается на терминале пользователя
  -> sudo -n falco ...     # сам запуск уже без вопроса, вывод перехватывается
```

Разделение на два вызова непринципиально и сделано намеренно: `sudo -v`
наследует терминал, поэтому запрос пароля **виден**; `sudo -n` не спрашивает,
поэтому вывод falco можно разобрать как JSON. Один вызов с перехватом
невозможен — либо пароль не видно, либо JSON не прочитать.

- `sarbar scan --no-sudo` — не спрашивать, пропустить falco с явной пометкой
- `sudo sarbar setup --driver` — разовая установка eBPF-драйвера
- если пользователь root, sudo не используется вовсе

**Чего я не проверил:** сам интерактивный ввод пароля. У меня нет TTY и нет
пароля — `sudo -v` здесь возвращает «a terminal is required». Проверялась
логика: отказ sudo даёт `unavailable` с понятным текстом, успешная
авторизация приводит к префиксу `sudo -n` в argv, `--no-sudo` не вызывает
запрос вообще. Сам диалог с паролем владелец увидит при первом же
`sarbar scan <контейнер>`.

#### F.3 «Дай мне разрешения, которых не хватает»

Права на Docker-сокет: сокет `srw-rw---- root:docker`, группа `docker`
существует (gid 986), пользователь `d` в неё **не** входит. Вход в группу
`sudo` есть, но к сокету это отношения не имеет.

```
sudo usermod -aG docker $USER
# затем перелогиниться: Ctrl+Alt+F2, вход, обратно
# либо временно в этой же сессии:
newgrp docker
```

Это в точности то, что нужно, и ничего больше: `docker.sock` даёт полный
контроль над демоном, поэтому выдавать его стоит осознанно. Права на запись в
`/usr` и `/etc` пользователю не нужны и не выдаются — там достаточно
`sudo bash install.sh`.

#### F.4 Дефект, который нашёл я сам: тест ломал реальную установку

`_publish()` брал каталог из `os.path.expanduser("~/.local/bin")`. А
`os.path` — это **общий модуль** `posixpath`, и подмена `expanduser` в одном
тесте делалась глобальной. Тест `install_trivy` без своей подмены создавал
симлинк в **настоящем** `~/.local/bin/` и затирал рабочую ссылку на бинарник
165 МБ. Обнаружено при `test_console_format_honours_output`, который вдруг
получил `trivy exit=0, no report: Version: 2.0` — версию из фикстуры.

Исправлено в коде, а не в тесте: `_publish()` получает `Layout` и берёт каталог
из `lay.local_bin`. Тест может подменить путь, не трогая настоящий дом.
Закреплено `test_publish_never_touches_the_real_home`.

**Общий вывод:** любой production-код, который пишет в `$HOME`, обязан
получать этот путь через внедряемый объект. Иначе первый же тест тихо съест
рабочую систему.

#### F.5 Убрана мёртвая проверка

`falco_driver_state()` содержала `if probe.returncode == 0 ...: pass` — код,
который ничего не проверял и ничего не делал. Она заменена на честную версию:
`falcoctl` установлен или нет, а реальное состояние драйвера устанавливается
фактическим запуском falco при сканировании. Проверять это гаданием по выводу
`falcoctl` — значит врать.

Владелец предположил, что `risk.py` относился к удалённым `sarbar-checks`.

|---|---|

страхует вердикт, нельзя: страхуют пороги.

достигается быстро — 5 CRITICAL, 8 HIGH, 25 MEDIUM, 34 LOW, дальше число

### Сессия G — подготовка к GitHub: одна команда, две дыры в falco, честный офлайн

#### G.1 Решение владельца о модели поставки

Владелец: «проект будет лежать на GitHub, и человеку нужна одна команда, как у
trivy». До этого момента установка была только из клона — то есть для
разработчика. Новая схема:

```
curl -sfL https://raw.githubusercontent.com/OWNER/sarbar/main/install.sh \
    | sudo bash -s --
```

`install.sh` теперь определяет, откуда он запущен:

| Ситуация | Источник |
|---|---|
| Рядом есть `pyproject.toml` | локальный клон, ставится как есть |
| Запущен по конвейеру из сети | скачивается `codeload.github.com/OWNER/sarbar/tar.gz/main`, распаковывается с `--strip-components=1`, и ставится этот исходник |

Проверено на живом публичном репозитории: скачивание, распаковка и проверка
`pyproject.toml` работают. Пока `REPO` в скрипте равна заглушке `OWNER/sarbar`,
он **отказывается работать** и объясняет, что надо поменять, — молча ставить
нечего.

#### G.2 Дыра №1: `falcoctl` не устанавливался

```
/usr/bin/falco
/usr/bin/falcoctl                     <-- не ставился
/etc/falcoctl/falcoctl.yaml           <-- не ставился
/usr/share/falco/plugins/libcontainer.so   <-- не ставился (дыра №2)
/usr/lib/systemd/system/falco-*.service
```

`sudo sarbar setup --driver` вызывает `falcoctl container install`. Команды
`falcoctl` в системе не было, поэтому подсказка «выполните setup --driver»
была **нерабочей**: она вела в тупик.

Исправлено: `install_falco` кладёт `falcoctl` рядом с `falco`, а
`falcoctl_path()` ищет его и в `PATH`, и в раскладке, куда ставили.

#### G.3 Дыра №2: плагин контейнеров не устанавливался

Falco без `libcontainer.so` выдаёт:

```
Error: Plugin requirement not satisfied, must load one of: container
```

и **не может** наблюдать контейнер. При этом он печатает `Events detected: 0`,
то есть сообщает «ничего не нашёл» вместо «не смотрел». Именно такой случай
SPEC запрещает инвариантом I-1.

До правки плагина не было на диске вообще — его положили в тот же
`~/.sarbar/bin`, а не в `usr/share/falco/plugins`.

#### G.4 Третья находка: `-L` — это не флаг плагинов

Первая попытка починить №2 была `-L <каталог плагинов>`. Оказалось, в falco 0.45
`-L` означает «показать список правил и выйти». Настоящий рецепт найден
экспериментально:

```
-o plugins[0].library_path=/абсолютный/путь/libcontainer.so
-o load_plugins=container
```

Две отдельные вещи:

1. **`load_plugins: []`** — в falco 0.45 плагин container **выключен по
   умолчанию**, хотя `falco_rules.yaml` его требует. Без явного включения
   получается ровно ошибка «Plugin requirement not satisfied».
2. **`library_path: libcontainer.so`** — голое имя файла, которое falco ищет в
   `/usr/share/falco/plugins`. Установка без root туда писать не может, поэтому
   нужен абсолютный путь.

Значение `-o` передаётся **без квадратных скобок**: `load_plugins=[container]`
falco воспринимает как имя `[container]` и отвечает «plugin config not found for
given name».

Индекс `plugins[N]` **читается из конфига**, а не считается равным нулю: если у
пользователя первым listed другой плагин, нулевой индекс указал бы на чужой
`.so`. Закреплено `test_plugin_index_is_read_from_the_config_not_assumed`.

Проверено на живом бинаре: `falco --list-plugins` показывает
`1 Plugins Loaded: Name: container, Version: 0.7.4`, и falco доходит до следующей
ошибки — драйвера:

```
libpman: ring buffer map type is not supported (errno: 1 | message: Operation not permitted)
Events detected: 0
```

#### G.5 Полнота установки falco теперь проверяется

`_falco_missing(lay)` возвращает список того, чего нет. Установка считается
успешной только когда есть **и** бинарник, **и** `falcoctl`, **и** плагин.
Недостаточная установка помечается `partial:` и **переустанавливается**, а не
объявляется рабочей.

| Состояние | Сказано пользователю |
|---|---|
| нет `falcoctl` | «no way to install the driver» |
| нет плагина | «falco cannot watch containers» |
| всё есть | «ok» |

#### G.6 Третий случай: тест снова полез в настоящий `$HOME`

Новый тест `test_container_plugin_is_found_where_we_installed_it` создавал и
**удалял** `~/.local/share/falco/plugins/libcontainer.so` — то есть стирал
настоящую установку, второй раз в этом проекте (первый — симлинк на trivy в
сессии F).

Переписано: список каталогов поиска перенаправляется в `tmp_path` через
`monkeypatch.setattr(FalcoEngine, "PLUGIN_DIRS", ...)`. Добавлен отдельный тест
`test_container_plugin_search_list_covers_both_layouts`, который проверяет, что
в списке есть и системный, и пользовательский путь — чтобы редирект в тесте не
ослепил реальный код.

**Правило, которое из этого следует:** любая константа, содержащая путь внутри
`$HOME`, обязана быть атрибутом класса или параметром, иначе первый же тест
съест рабочую систему. Второй раз подряд — это уже не случайность, а
недостающая проверка в ревью.

#### G.7 Найдена и починена поломка `sarbar offline` для Dockerfile

Живая проверка показала:

```
sarbar offline Dockerfile
-> trivy exit=1, no report: FATAL Fatal error unknown flag: --skip-db-update
-> Mode DEGRADED, Verdict FAIL
```

sarbar отработал честно (не тихий PASS), но функция была сломана. Причина:
флаги офлайна одни и те же для всех подкоманд, а они разные (сверено с
`trivy --help` версии 0.75):

| Подкоманда | `--skip-db-update` | `--offline-scan` | `--skip-check-update` |
|---|---|---|---|
| `trivy image` | есть | есть | есть |
| `trivy fs` | есть | есть | есть |
| `trivy config` | **нет** | **нет** | есть |

`trivy config` вообще не работает с базой уязвимостей, поэтому и не знает этих
флагов. Исправлено через `TrivyEngine.OFFLINE_FLAGS` с ключом по виду цели,
закреплено двумя тестами.

Почему не поймали раньше: офлайн проверяли на папке (`fs`), где флаги верные.
Dockerfile-ветку в живом режиме не прогоняли.

**Проверка после починки, сеть отключена на уровне ядра** (`unshare -rn`):

| Цель | Сканер | Риск | Вердикт |
|---|---|---|---|
| `Dockerfile` | trivy | 39.0 | FAIL |
| `examples/` | trivy | 56.8 | FAIL |

#### G.8 История переехала в `XDG_STATE_HOME`

Владелец спросил: «история правда должна лежать в `/var/lib`?». Нет.

Спецификация XDG Base Directory, раздел 3, дословно:

> `$XDG_STATE_HOME` … contains state data that should persist between
> (application) restarts, but that is not important or portable enough to the
> user that it should be stored in `$XDG_DATA_HOME`. It may contain: **actions
> history (logs, history, recently used files, …)**

`/var/lib` — это состояние демонов: на машине `/var/lib/apt`, `/var/lib/dpkg`,
`/var/lib/docker`, все с правами root. История запусков человеком туда не
относится.

| | Было | Стало |
|---|---|---|
| Путь | `/var/lib/sarbar/history.db` (root) или `~/.sarbar/history.db` | `$XDG_STATE_HOME/sarbar/history.db` |
| По умолчанию | — | `~/.local/state/sarbar/history.db` |
| Права | — | каталог `0700` |

Старая база **переносится** при первом обращении (`migrate_legacy`), чтобы
upgrade не терял историю. Относительный `XDG_STATE_HOME` игнорируется — так
требует спецификация.

#### G.9 Установщик от root делает всё, включая драйвер

`sudo bash install.sh` теперь: Python → sarbar → trivy → falco + falcoctl +
плагин → **драйвер** → проверка → подсказки.

| Флаг | Действие |
|---|---|
| `--no-driver` | не грузить драйвер (root по умолчанию грузит) |
| `--no-scanners` | только sarbar, без скачивания сканеров |
| `--ref TAG` | ставить тег, а не ветку |

`uninstall.sh` знает про `falcoctl`, `/etc/falcoctl`, `/usr/share/falco` и
спрашивает про каждый отдельно.

#### G.10 Что честно НЕ сделано автоматически

**Права на docker.** Сокет `docker.sock` равносилен root на хосте. Установщик
печатает точную команду, но **не** выполняет `usermod`: это решение владельца
машины, а не установщика.

#### G.11a Причины, по которым одна команда не работала сразу

| Причина | Проверка |
|---|---|
| В `install.sh` стояла заглушка `OWNER/sarbar` | заменено на `doisss/cast`, репозиторий взят из `git remote` |
| Репозиторий `doisss/cast` на GitHub **пуст** | `api/repos/doisss/cast/commits` → `Git Repository is empty`, 0 веток, raw отдаёт 404 |
| Пушить нечем | нет `credential.helper`, нет `~/.ssh`, `git push --dry-run` → `could not read Username` |

То есть 404 был не ошибкой скрипта: коммитов на GitHub не существует. Всё
закоммичено локально (два коммита), остаётся только `git push` — это требует
учётных данных, которых у меня нет.

#### G.11b `.gitignore` прятал модуль отчётов

Строка `report.*` в `.gitignore` совпадала не только с выводом отчёта, но и с
`sarbar/report.py` и `sarbar/policies/report.yaml`. Оба файла никогда не были
в индексе git. Последствие: колесо, собранное из репозитория, не содержит
модуля отчётов, и установка с GitHub дала бы пакет, не умеющий делать отчёт.

Исправлено: шаблон ограничен корнем репозитория (`/report.json` вместо
`report.*`). Проверено сборкой колеса из свежего клона: `sarbar/report.py`,
`sarbar/setup.py`, `sarbar/policies/*.yaml` на месте, точки входа `sarbar` и
`cast` обе.

#### G.11c Живой обход инварианта I-1: `sarbar scan -e none`

```
$ sarbar scan -e none ./Dockerfile
│ Scanners │ (none)
│ Mode     │ DEGRADED — no external scanner produced results
│ Verdict  │ PASS          ← и код возврата 0
```

Причина: переход из `DEGRADED` в `FAIL` требовал непустого списка причин-диагностик
(`not used` / `cannot work without network`). При `-e none` ни один сканер не
запускается, поэтому ни одной диагностики не возникает, список пуст, и вердикт
оставался `pass`. В CI это худший из возможных исходов: зелёная сборка, которая
ничего не проверяла.

Исправлено: условие безусловное — деградация при `fail_on_degraded` всегда даёт
`FAIL`. Профиль, которому ворота не нужны, существует отдельно и называется
`report`.

Закреплено тремя тестами, один из которых проверяет обратное: сканер, который
отработал и не нашёл ничего, `PASS` получать **должен**. Иначе починка
сломала бы честный зелёный свет.
